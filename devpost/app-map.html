Ember: app map

A pacing planner that projects today's overspend onto the next three days and learns each person's crash lag. Everything runs in the browser; data lives in local storage.

The main pieces

  • Model (src/model/): pure functions with no UI. They cover the forecast, the learning fit, the quick-add parser, swap suggestions and sample data. This is where the idea lives, and it is unit-tested.
  • Store (src/state/store.tsx): one reducer holds settings, today's check-in and plan, and history. It saves to local storage on every change and rolls the day over at midnight.
  • Screens (src/components/): Welcome, Today (energy hero, plan builder, forecast, swaps), Pattern (stats and history chart) and Settings.

One action, end to end: adding a birthday party

Reference route

A reference route through the actual code. It was not walked through interactively.

1
src/components/PlanBuilder.tsx → QuickAdd
The form's submit calls parseQuickAdd(text) and dispatches the new items. That's the moment a sentence becomes plan items.
2
src/model/quickAdd.ts → parseQuickAdd
It splits the sentence into phrases, pulls out durations with extractMinutes, and matches each phrase to the activity library (matchActivity). "birthday party" becomes Family gathering, costing 5 spoons.
3
src/model/forecast.ts → projectDays
It works out today's overspend and spreads ratio × weights[k] × over onto days +1 to +3, alongside payback still owed from logged days. The learned weights and ratio come from fitPattern in src/model/learn.ts. Forecast.tsx renders the result, and Friday turns Crash likely.

To change this, start here

  • Activity costs, or adding an activity: the ACTIVITIES list in src/model/activities.ts.
  • When a day counts as "Tight" or "Crash likely": CRASH_LINE and TIGHT_LINE in src/model/forecast.ts.
  • Check-in levels and their envelopes: CHECK_IN_LEVELS in src/model/forecast.ts.
  • Colours and themes: src/styles/tokens.css.
  • Swap ideas: the candidate loop in suggestSwaps, src/model/swaps.ts.

A practice to reuse

The riskiest assumption was whether a small least-squares fit could really recover a person's crash lag from a few weeks of noisy data. The spec (spec.md › Decisions and Open Issues) named that as an open question, and it was settled by a test rather than by hope. src/model/model.test.ts generates history from a known pattern and asserts that the fit recovers it. The same move works on any project: when a feature rests on an uncertain algorithm, build fake data where you know the right answer and check that the code finds it. Do that before building UI on top.

Run it again

npm install, then npm run dev, then open http://localhost:5173. Run the tests with npm test.
